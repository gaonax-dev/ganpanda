# 동기화와 저장

## 요약
프로젝트 문서는 기기(IndexedDB)에 항상 저장되고, 서버가 연결되면 실시간으로 합쳐집니다. 이미지는 문서와 따로, 내용 해시를 키로 저장합니다.

## 상태
- 기기 저장: 구현됨 (`y-indexeddb`, `src/lib/assets.ts`)
- 서버: 구현됨 (`server/`) → [../server/api.md](../server/api.md)
- 앱 ↔ 서버 연결: 구현됨 (`src/lib/sync.ts`, 1차 1-1)

## 앱 연결 (`src/lib/sync.ts`)
- 서버 주소: `VITE_SYNC_URL`. 없으면 개발 중에는 `http://localhost:8787`, 운영 빌드에서는 **서버 없이 로컬 모드**(`core/syncUrl.ts`).
- 공식 `y-websocket` 클라이언트로 `${서버}/api/rooms/<room>`에 접속합니다. 끊기면 자동 재접속합니다.
- 연결 상태 `app.sync`: `local`(서버 없음) / `connecting` / `online` / `offline`(재연결 중). 상단 바에 표시(`data-testid="sync-status"`).
- 접속자 상태(awareness): `{ name, color, cursor? }`. 색은 이름으로 정해집니다(`core/presence.ts`). 같은 이름의 탭 여러 개는 한 사람으로 합쳐 상단 바에 표시하고, 커서는 탭마다 사진 보드에 보여 줍니다(world 좌표, 50ms 간격 전송).
- 접속자 목록은 `name`이 없는(아직 상태를 보내지 않은) 접속을 제외합니다. 이름이 빈 문자열이면 "손님"으로 표시합니다.

## 방(room)
- 프로젝트 하나 = 방 하나. URL `?room=<id>`. 서버가 있는 빌드에서는 **등록된 프로젝트만** 접속되고(`/api/projects/:id/access`), 자격은 WebSocket 쿼리 `?session=` 또는 `?invite=`로 넘깁니다 → [../features/projects-invites.md](../features/projects-invites.md). 서버 주소가 없는 빌드는 `local-default`.
- 방 ID 형식(서버 검사): `^[A-Za-z0-9_-]{6,64}$`
- E2E 테스트는 테스트마다 다른 방을 써서 서로 섞이지 않게 합니다.

## 동기화 프로토콜
- **y-websocket 호환**입니다. 앱은 공식 `y-websocket` 클라이언트를 그대로 씁니다(1차 예정).
- 메시지 첫 값(varUint): `0` 동기화, `1` 접속자 상태(awareness), `3` 접속자 상태 요청
- 연결 직후 서버가 자신의 상태 벡터(sync step 1)를 보내고, 클라이언트도 step 1을 보내 서로 빠진 부분을 교환합니다.
- 오프라인 편집은 다시 연결될 때 자동으로 올라갑니다(서버 테스트로 확인).

## 실시간 방 비용 줄이기 (2026-10-27)
사용자: "내가 간판집 무료로 하면 1000명당 비용은?" → "하루에 1000$는 감당하기 어렵지" → "진행해주고". 실시간 방(Room Durable Object)은 웹소켓 최대 절전(hibernation)이라 할 일이 없으면 잠들어 접속 시간 과금이 멈춘다. 그런데 방을 계속 깨우는 것이 둘 있었다.
- **재연결**: y-websocket 은 30초 동안 서버에서 받은 게 없으면 다시 연결한다. 혼자 있는 사람에게는 서버가 보낼 것이 없어 **30초마다 다시 연결**했다(권한 확인 DB 3번 + 방 깨우기 + 동기화). → 클라이언트가 20초마다 `'ping'` 문자열(`sync.ts PingSocket`), 방은 **깨지 않고 자동 응답** `'pong'`(`room.ts setWebSocketAutoResponse`). 클라이언트는 `'pong'` 을 y-websocket 이 읽는 빈 접속자 메시지 `[1,1,0]` 로 바꿔 넘긴다(받은 시각만 갱신).
- **접속자 표시 갱신**: y-protocols 는 15초마다 내 표시를 다시 보낸다. → **혼자인 지 5초**면 내 표시를 거둬(`setLocalState(null)`) 갱신을 멈춘다. 누가 들어오면 그쪽이 먼저 알리고, 그걸 받으면 다시 표시한다. 쉬었다가 이어 붙일 때도 다시 알린다(둘 다 조용해져 서로 못 보는 일이 없게).
- **연결 쉬기**(`paused`, 상단 "쉬는 중 · 손대면 다시 연결"): 화면을 안 본 지 **15초**(`HIDDEN_PAUSE_MS`) 또는 손대지 않은 지 **5분**(`IDLE_PAUSE_MS`, 누르기·키·휠·터치)이면 연결을 끊는다. 다시 보거나 손대면 바로 이어 붙인다 — 편집은 기기(IndexedDB)에 있고 이어 붙이면 올라간다. 쉬는 동안 다른 사람의 변경은 이어 붙일 때 받는다.
- 결과: 과금되는 시간이 "열어 둔 시간"에서 "실제로 주고받는 시간"으로. 테스트 `tests/e2e/syncIdle.spec.ts`(혼자 40초: 재연결 0·바이너리 전송 0·ping 만, 둘이 서로 보임, 숨김·손 안 댐 → 쉼 → 이어 붙임). 개발 모드는 `localStorage ganpanda.test.syncTiming` 으로 시간을 줄여 시험한다.

## 기기 자료로 먼저 열기 (2026-10-27)
사용자: "프로젝트 로딩이 너무 느리다. 앱과 웹에서 모두 로컬에 자료를 가지고 있으면 안될까?" → "프로젝트 오픈에도 한참 걸린다 아무것도 없는데" → "남은 것에 답이 있었네 진행해줘".
전엔 문서가 기기에 있어도 **계정 확인(/api/me) → 권한 확인(/access, 서버 DB 5~7번 차례로) → 기기 문서 읽기 → 접속**이 줄줄이였고, 사진 없는 프로젝트는 서버 첫 동기화(또는 4초)까지 "불러오는 중…"이었다.
- **권한 기억**(`src/lib/localOpen.ts`, `localStorage ganpanda.access.<room>` = 받은 권한 + 누구로 열었나(세션 끝 12자 | 초대 토큰)): 같은 로그인·같은 초대로 다시 열면 기억한 권한으로 **기기 문서(IndexedDB)를 바로** 열고 접속도 바로 시작, 서버 확인은 뒤에서(`verifyAccess`). 401·403·404 면 접속을 끊고 기기 문서를 지우고(`clearData`) 기억도 지운 뒤 "접근 불가" 화면. 인터넷 문제면 기기 문서로 계속. 역할이 바뀌었으면 새로 고침. 처음 여는 방은 전처럼 확인 뒤에.
- **계정 확인과 방 열기를 나란히**(`init`): 견적 초안 방(가게 사장)만 계정이 있어야 방이 정해져서 차례로. 소유자 새 프로젝트의 기본 단가 복사는 계정을 받은 뒤(`authDone`).
- **연 적 있는 사진 없는 프로젝트**는 동기화를 기다리지 않고 바로 빈 화면(`boardSettled` 의 `openedBefore`). 사진이 있던 곳(`hadPhotos`)은 전처럼 로딩 스피너.
- **내 계정 기억**(`ganpanda.meCache`, 같은 세션만): 홈·메뉴를 기억한 계정으로 바로 그리고 서버 답으로 바꾼다. 인터넷 문제면 기억한 계정으로 계속, 로그아웃·만료면 지운다. 기억한 계정에는 화면 값만 쓰고 서버 호출 같은 부수 효과는 없다(`applyCachedMe`).
- **홈 목록 기억**(`ganpanda.home.<계정>` = 프로젝트·그룹·그룹 계산서): 먼저 보여 주고 서버 목록으로 바꾼다. 로그아웃하면 지운다.
- 테스트 `tests/e2e/localOpen.spec.ts`(권한 확인 8초 지연에도 3초 안 사진, 권한 확인 실패(오프라인)에도 열림, 404 면 닫고 기기 문서 지움, 빈 프로젝트 1.5초 안 빈 화면, 홈 목록 서버 8초 지연에도 2.5초 안).
- 다른 기기에서 처음 여는 프로젝트는 여전히 서버를 기다린다(기기에 아무것도 없다).

## 에셋
- 에셋 ID = 내용 SHA-256 앞 16바이트(32자 hex). 클라이언트와 서버가 같은 방식으로 계산합니다.
- 기기에서는 IndexedDB(`ganpanda-assets`)에 둡니다.
- 서버에서는 R2에 두고, 업로드할 때 해시를 검증합니다.
- 에셋 요청에는 프로젝트 자격(`?project=&session|invite`)이 붙습니다(`setAssetScope`, 방 진입 후 설정).
- 업로드(`putAsset`): 서버에 `HEAD`로 있는지 확인하고 없으면 `PUT`한 뒤 기기에 저장. 용량 한도 초과(413 `storage_limit`)면 저장하지 않고 `StorageLimitError` → 상단 알림. 네트워크 실패는 보관했다가 다시 연결될 때 재시도(`flushPendingUploads`) — **2026-10-17**: 재연결 때만이 아니라 5초→15초→45초→2분 간격으로도 다시 올리고(`schedulePendingFlush`), 자격(`setAssetScope`)이 늦게 오면 그때 올립니다. 연결이 끊긴 적 없이 한 번 실패한 사진이 휴대폰에만 남아 다른 기기에 안 보이던 경우를 막습니다.
- 동시접속 한도(429)로 접속이 거부되면 y-websocket 이 재시도하는 동안 앱은 3초마다 `/access`의 좌석 현황을 확인해 안내 배너를 보여 주고, 연결되면 지웁니다. 안내 배너(동시접속·새 버전·알림, `App.svelte` `.banners`)는 본문 위에 **떠 있는 겹층**(absolute)이라 나타나고 사라져도 아래 화면이 밀리지 않습니다(2026-10-18 사용자: "화면이 재정렬되고 사라지면 다시 제위치로 간다. 이건 문제다").
- 다운로드(`assetUrl`): 기기에 없으면 서버에서 받아 기기에 저장합니다. **2026-10-17**(사용자: "이미지가 기기에서 오는데 오래 걸리거나 모바일에서는 누락되는 경우도 있다"): 같은 에셋 동시 요청은 한 번만 받고(`inflight`), 서버 받기는 30초 제한 + 5회 재시도(0.7→8초), 브라우저가 오프라인이면 `online` 까지 기다렸다가 받습니다. 404/403 만 즉시 "없음". 끝내 못 받은 에셋은 `missing` 에 두었다가 다시 연결될 때 받고(`retryMissingAssets`, `whenOnline`), 받으면 `onAssetsRecovered` → `app.assetEpoch` 가 바뀌어 에셋을 쓰는 화면(보드 사진·리스트 카드·디자인·첨부·구성 요소 그림·제안 이미지)이 다시 요청합니다. IndexedDB 를 못 여는 환경(사생활 보호 모드·용량 부족)에서도 서버에서 바로 받아 보여 줍니다.
- **휴대폰 메모리**(2026-10-18 사용자: 아이폰 크롬 "이 페이지를 열 수 없음" = 웹 프로세스 크래시): 표시용 사진(`photoDisplay.displayUrl(assetId, {w,h})`)은 원본을 통째로 디코딩하지 않고 `createImageBitmap(blob, {resizeWidth})` 로 줄인 크기만 디코딩(크기를 모르거나 지원 안 하면 옛 경로), 사진 위·카드의 입힌 디자인(`DesignFace`)도 원본 페이지 대신 줄인 사본. **2D 겹침 층은 표시 px 크기**(`PhotoZone` `.designs`: 전에는 사진 원본 px 크기(예 4000×3000 CSS px)로 만들고 `transform: scale` 로 줄였는데, WebKit 은 그 층의 백킹 스토어를 원본 크기로 잡아 사진 여러 장이면 수백 MB → 핀볼 프로젝트에서 "이미지가 로딩 완료되고 다시 로딩 완료되고 에러 화면"). 진단용 `?safe=1`(`app.safeMode`): 2D 겹침(바탕·테·디자인·글자)과 카드 얼굴을 끈다 — 그래도 죽으면 겹침 레이어가 원인이 아님.
- **사진에서 만든 그림도 기기에 저장**(`src/lib/derivedImages.ts`, IndexedDB `ganpanda-derived`, 2026-10-27 사용자: "프로젝트 로딩이 너무 느리다" → "사진이 가장 크다 … 이미지는 거의 변경이 없다"): 원본은 이미 기기에서 읽었지만, 열 때마다 표시용 줄인 사본과 평면도 카드 얼굴을 원본 디코딩·축소·JPEG 굽기로 **한 장씩 줄 세워** 다시 만들었다. 이제 원본 ID(내용 해시라 바뀌지 않음) + 만드는 조건을 키로 기기에 두고(`d|<asset>|<표시 긴 변>` = 사본 또는 "원본 그대로", `f|<asset>|<사진 폭>|<영역>|<크기>` = 카드 얼굴), 있으면 대기열 없이 바로 쓴다. 600개를 넘으면 오래된 것부터 450개로. 저장 못 하면 전처럼 만든다. 측정(사진 6장 4000×3000, CPU 4배 느리게): 다시 열 때 사진이 다 보일 때까지 1.75~2.1초 → 0.55~0.7초. 테스트 `tests/e2e/photoDisplayCache.spec.ts`.
- **올리기 전 줄이기**(`photoPrep.ts` `prepareUpload`, 2026-10-17): 사진은 긴 변 **3200px**(`UPLOAD_MAX`) 로 줄여(JPEG 0.9, EXIF 회전 적용) 올립니다 — 휴대폰 12MP 사진 3~6MB 가 1MB 안팎으로. 사진 좌표는 올린 에셋 px 기준이라 올리기 전에만 줄이면 일관됩니다.

## 에셋: 기기 먼저, 서버는 뒤에서 (2026-10-19)
사용자: "모바일에서 카메라로 촬영하고 나서 프로젝트로 올라오는 시간이 너무 오래 걸린다. 우선 내부에서 가져다 쓰고 캐시에 가지고 있고 캐시가 없어지면 그때 서버에서 가져오게". 전엔 `putAsset` 이 서버 업로드(HEAD + PUT)를 기다린 뒤 돌려줘서, 휴대폰 데이터에서는 촬영 후 보드에 올라오기까지 업로드 시간만큼 걸렸다.
- `putAsset`(`src/lib/assets.ts`): 기기(IndexedDB)에 저장하고 **바로 돌려준다**. 서버 업로드는 뒤에서(`flushPendingUploads`, 한 번에 하나씩, 실패하면 5초→15초→45초→2분). 사진은 바로 보드에 올라오고 문서(사진 항목)도 바로 동기화된다.
- **올릴 목록 기억**: `localStorage` `ganpanda.pendingAssets` = `[{id, project}]`. 업로드 전에 앱을 닫아도 다음에 그 프로젝트를 열 때(`setAssetScope`) 기기에서 꺼내 이어서 올린다. 성공·한도 초과면 목록에서 뺀다.
- **받는 쪽**: 다른 기기는 업로드가 끝나기 전에 받으러 올 수 있다. 서버는 아직 없는(그 계정에 등록 안 된) 에셋에 GET·HEAD 모두 **404**(전엔 GET 이 403 이라 받는 쪽이 바로 포기했다). 받는 쪽은 404 도 재시도(5회, 점점 길게)하고, 그래도 없으면 20초마다 다시 받아(최대 10분) 받으면 화면을 다시 그린다(`onAssetsRecovered` → `app.assetEpoch`).
- 올리는 동안 새로 들어온 것도 이어서 올린다(PDF 페이지처럼 잇달아 들어올 때 첫 것만 올라가고 나머지가 재시도 타이머를 기다리던 것). 서버가 받지 않는 형식·요청(400·413·415, 예: `.ai` 원본 application/postscript)은 다시 올려도 같으므로 목록에서 뺀다(기기에는 남는다).
